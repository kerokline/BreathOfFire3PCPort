# What a player install still lacks, by source: the census

**Status:** IN PROGRESS (verified 2026-10-17 against `origin/main` `cf809700`;
a reading and counting pass - no game run, no capture, nothing fixed, no
recipe regenerated. Section 8 rewritten 2026-10-18 with each item's status
after the install-gap round, at `install-gap/round` `0baf26f7`; sections 0..7
are the 2026-10-17 census as it was)

A census of what each kind of player install - PC-only, PSX-only (`psx-jp`,
`psx-us`, `psx-eu-en`, `psx-fr`, `psx-de`), PSP-only (`psp-jp`, `psp-eu`) -
still lacks, and whether each item still needs fixing. Most of it is the
exe image (`base/exe/data.bin`) a disc-only install builds from its disc, where
bytes no disc carries stay zero; section 7 is the rest of the install. It folds
in [`exe-engine-own.md`](exe-engine-own.md) 4, [`disc-gap-fills.md`](disc-gap-fills.md),
[`exe-image-twins-1013.md`](exe-image-twins-1013.md) 6,
[`disc-data-inventory.md`](disc-data-inventory.md) 5,
[`exe-chinese-remaining.md`](exe-chinese-remaining.md) 5-7,
[`disc-only-install.md`](disc-only-install.md) 2-3 and the defect list
([`known-defects.md`](known-defects.md)) rather than redoing them. Addresses,
classes, symbol names and counts only (CLAUDE.md rule 1).

## 0. What came out

1. **Every row of `recipes/exe-gaps.tsv` has a status** (sections 2-5): 359 to
   388 rows per disc build. The 120 gap items (a symbol's rows across builds)
   are 105 **NEEDS FIX**, 13 **OWNER CALL** and 2 **HARMLESS**. The language,
   unread and key rows are 1 IN FLIGHT (issue #77), 1 FIXED and the rest
   HARMLESS, with seven NEEDS FIX exceptions (section 5).
2. **Five zero format strings or glyphs not filed as defects** (the D254 class,
   section 4.1). Each makes a screen draw nothing where the PC draws text:
   - a level-up's learned-ability names (Western PSX);
   - the field menu's play-time colon (every disc build);
   - the faerie village board's rows (every build);
   - the area-104 countdown (every build);
   - the area-75 counters (PSX).
   Each is a few bytes, and could be an engine-own string like D254's `%X`.
3. **Three gameplay-reaching gaps** found by reading their readers:
   - the village hi-lo game's payouts (`CommuHiLo_DealSteps`, every build,
     disc-unplaced, so the disc holds them);
   - a master's requirement list on the Western images
     (`MasterWin_Requirements+0x44`);
   - the event battles' track words (every build; already the owner's
     "track half").
4. **The defects already filed are still open** where they were: D266, D267,
   D268, D278, D282 (in flight), D286 FR / DE, D289, D246, D257, D279 / D280.
   D278's `?` marks share a gap row with `TornadoMote_Phases` on all seven
   builds, not only the Western ones.
5. **The owner's test install `C:\Users\kerok\bx`** (psx-us, generated
   2026-10-15) leaves `0x669868..0x669883` a gap. `FilledSince()` refuses an
   image like that, so it needs a rebuild under alpha.3 (HANDOFF item 11).

## 1. Method and sources

- **The rows:** `recipes/exe-gaps.tsv` at `cf809700`, last regenerated by
  `67d23959` (2026-10-16, I43 step 1). How each class is treated:
  `src/hook/exe_image.cpp`'s class table (`gap`, `language`, `unread` zero;
  `keys` written by `Shell_MapDefaultKeys`; a `gap` logged and, under
  `BOF3X_EXEIMAGE_STRICT=1`, a Fatal) and `FilledSince()`.
- **PC non-zero bytes per row:** counted from `bof3\BOF3.exe`'s `.data` with
  `exe_tables.pc_data` (session script `count.py`).
- **Readers:** three sources, all through session scripts `xr.py`, `ctx.py`
  and `readers.py`.
  - Capcom's instructions: `analysis/pc_xref.json`, operands inside a row or
    at its table's base below it, named by `symbols.toml`'s `[[func]]`.
  - `src/`'s named constants (`*_callees.h`).
  - `src/`'s mentions of the symbol.
  - Every reader named is ours now (10,088 functions in the exe host), and it
    reads the same address.
- **Windows on the disc:** found / tried, for the `disc-unplaced` rows. Read
  from `analysis/exe_own_1017/<build>.own.tsv`, a `tools/exe_own.py measure`
  output in the main checkout's `analysis/` dated 2026-10-17 07:27-07:33. It
  is not this census's own run, and its region counts differ from the
  committed rows by one or two per build.
- **Zero in a real image, confirmed:** read-only reads of `data.bin` in the
  A/B/C harness caches (`C:\Users\kerok\ab*`) and in `C:\Users\kerok\bx\cache`
  (psx-us, 2026-10-15). At `0x654900`, `0x6637E0`, `0x653084`, `0x61BC74`,
  `0x60ABF0`, `0x61FBD0` and `0x65C374`, every psx-us image has 0 non-zero
  bytes where the PC has 2, 1, 11, 9, 10, 3 and 4.
- **What a zero does:** read from the reader's code and the docs cited. No
  item here was played or captured for this census. "Not measured" means
  exactly that.

Statuses: **FIXED** (by what), **HARMLESS** (why), **IN FLIGHT** (someone is on
it), **OWNER CALL** (a decision the owner holds), **NEEDS FIX** with a candidate
source and a priority - P1 a screen or gameplay effect on a common path, P2 a
twin the disc search already locates or a PSP-specific value read on every
area, P3 the long tail (the owning-function method,
[`exe-import-engine.md`](exe-import-engine.md) 3.3), P4 no reader found.

### 4.1 The zero strings and glyphs not filed as defects (the D254 class)

D254 was a save slot number drawing nothing because its `Crt_sprintf` format
`%X` was zero. It was fixed by holding the string as the engine's own
(`exe_own.cpp`, DIV-0101 amended). The same shape is still open at five places.
Each is a format string or a one-glyph string read in place, so a zero gives an
empty string: nothing drawn, no crash. [`crt-rest.md`](crt-rest.md)'s format
table names four of the five; nothing in `known-defects.md` does.

| Address | Reader | Builds | What draws nothing |
